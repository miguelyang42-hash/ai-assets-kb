## Preconditions
- 已在 `{cron}` 中设置了定时外贸开发任务且近期有未执行记录。
- 明确目标产品类目 `{product_category}` 及每日获客配额。

## Workflow
1. **审计执行记录以识别缺口**：访问 `.accio` 账号目录下对应 Agent 的 `agent-core/diary` 文件夹，对比当前日期与历史日志，找出未执行任务的日期并量化缺失的线索总量。
2. **重算任务量并更新任务中心**：在任务列表中创建总控任务，将补发总量与当日新增量合并。根据缺口大小决定是否需要分批执行，以维持发信账号权重。
3. **调用子代理并行挖掘线索**：使用 `sessions_spawn` 派生子代理，针对缺失时间段的 `{product_category}` 需求，在 Amazon/eBay 等平台批量搜索并验证联系人，将结果汇总至工作区的 CSV 暂存区。
4. **部署具备断点续传能力的批量脚本**：准备 Python 发信脚本，通过子进程调用 `send_gmail_message`。脚本逻辑必须包含对已发送记录的检查（Skip Logic），并确保邮件模板包含 HTML 高亮及产品缩略图。
5. **后台执行并监控投递进度**：使用 `bash` 将批量脚本切入后台运行（防止前台超时），随后通过 `process(action="poll")` 定期轮询输出，直至所有补发邮件投递完成。

## Suggestions
- 在批量发信脚本中加入 30-120 秒的随机延时（Jitter），模拟真人操作以降低被拦截风险。
- 补发任务建议在设备在线的高峰时段优先执行，提高邮件被目标负责人看到的概率。
- 使用 `tail -f` 或重定向输出到 log 文件，方便通过 `read` 工具随时检查后台任务的详细报错。

## Pitfalls
- **Step 4**: 在使用 `edit` 修改脚本前必须先执行 `read` 操作，严禁直接在未加载上下文的情况下进行代码编辑，否则会导致脚本损坏。
- **Step 3**: 若子代理挖掘的线索来源高度重合，必须在 CSV 汇总阶段增加去重逻辑（Deduplication），避免同一客户收到多封重复邮件。
- **Step 5**: 严禁在脚本执行期间重复启动相同命令，应先通过 `process(action="list")` 确认旧进程状态，防止发信冲突。
